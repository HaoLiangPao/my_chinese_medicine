## IDEA-1 · 学堂：公开的药材介绍作为入口

**想法**：药材介绍（性味、归经、传统用途、产区……）是公开的知识，放进学堂，当作吸引普通人来学习的入口。学堂的其他内容改成注册登录以后才能用。

**和已有计划的关系**

- 0010 里计划的「公开药材介绍页」（LBL-5，药材标签上的二维码打开它）可以就是这个页面：`/learn/herbs/[id]`。做 LBL-5 时按这里的定位来设计
- 现在学堂全部公开（LEARN-1「不登录也能看」，E2E `learn.spec.ts` 也这么测）。改成部分公开要改 LEARN-1 的定义和测试
- 只显示**已审核**的资料（0010 §3.1）；未登录读资料只开放资料本身的列（`check_note`、`flag_note` 不开放）

**要想清楚的**

1. 学堂里哪些公开、哪些要登录？（药材介绍公开；五行图、阴阳图、学习路径呢？）
2. 药材介绍页怎么引导注册：页面上放什么入口、注册后落在哪里（病人账号？）
3. 搜索引擎收录和分享：标题、描述、分享图
4. 公开页面上不能有用药建议，只有「中药知识介绍」（CLAUDE.md）
5. 药材列表页（按拼音 / 按功效分类浏览），手机上怎么找药

## IDEA-2 · 药材关系图谱

**想法**：把药材之间的关系做成可以探索的图，比如：

- 炮制品 ↔ 原药材（已有数据：`herbs.base_herb_id`）
- 同一功效分类（已有：`herbs.category`，如补气药、补阴药）
- 性味、归经相同（已有：`herb_monographs`）
- 配伍禁忌：十八反、十九畏（现在写在「使用注意」的文字里，要单独整理成结构化数据并审核）
- 常用药对、方剂组成（新数据，需要来源和审核）
- 同名不同药（如南沙参 / 北沙参、广藿香 / 藿香）

**几种做法**

| 做法 | 好处 | 问题 |
|---|---|---|
| A. 用 Obsidian 做基座（每味药一篇 Markdown，用双链连起来，用它的关系图看） | 图谱现成、好用；写内容方便；适合我们自己整理、研究关系 | Obsidian 是桌面应用，图谱不能直接放进网页给用户用；Obsidian Publish 要付费，图谱交互有限；内容要和数据库同步（两份数据） |
| B. 树结构（功效分类 → 药材 → 炮制品） | 简单，手机上好用，数据现成 | 只能表达「属于」关系，表达不了配伍、禁忌这类横向关系 |
| C. 自己做交互式关系图（放在学堂里，数据来自数据库） | 和学堂的五行图、阴阳图风格统一；点一味药能跳到它的介绍页（接 IDEA-1）；关系类型可以筛选 | 工作量最大；关系数据要建表（比如 `herb_relations`）并且审核 |

**初步想法**（还没定）：A 和 C 可以组合：先用 Obsidian（或者直接用 Markdown 文件）把关系整理、审核出来；内容稳定以后导入数据库，再在学堂里用 C 展示。B 可以作为 C 在手机上的简化视图。

**要想清楚的**

1. 先做哪几种关系？建议从已有的结构化数据开始（炮制品、功效分类、归经），配伍禁忌和药对要审核以后才能公开
2. 关系数据谁来审核（和药材资料一样走核对页？）
3. 药方里两味药同时出现的统计（共现）是用户的数据，只能在自己的药柜里看，不能放进公开的图谱

## IDEA-3 · 基于已有药方开新处方（Prescription Reuse）

**Hao 的原话（整理）**

- 现在开方要一味一味选药、填克数，很重复。希望能**搜索并选一张已有药方**，把药材组合和克数导入新处方当作初稿，再按当前病人增删药材、调整克数。类似麦当劳的「再来一份」
- 搜索范围不只是当前病人的历史处方，也要能搜**其他病人**的药方（相似的病症可能用相似的药材组合）
- 筛选：「当前病人的历史药方」「预设药方」「全部可以访问的药方」
- 开出去以后是一份**独立的新处方**，以后修改不影响原来的药方
- 每次开方都会建新处方，时间一长搜索会很杂，所以**最常用的应该是预设药方**。前期药方少，医生复用了一张不是预设的药方时，保存时提醒「要不要存成预设药方」
- 只能看到有权限看的处方，不要多暴露其他病人的个人信息

**和现有功能的关系**

- CLN-6「从病历再开一张」已经能从**同一个病人**的病历出发开新处方（病人自动选好）。这个想法把它扩展成：可以从任何一张可以访问的处方或预设药方开始
- 处方本来就是独立的行（`prescriptions` + `prescription_items`），导入时复制药材和克数，天然不会影响原处方

**初步设计方向**（做之前写设计文档）

- 新表 `prescription_templates`（预设药方）：药柜、名字、药材和克数、脚注、备注、创建人；RLS 和处方一样按药柜隔离
- 「全部可以访问的药方」= 同一个药柜（同一个诊所）里的处方。别的诊所的处方看不到（RLS 本来就这样）
- 搜索结果里**不显示其他病人的名字和电话**，只显示处方名称、日期、药材组成（比如「黄芪 30、白术 12……」）；当前病人自己的历史处方可以显示日期
- 可以按药材搜（「含黄芪和党参的」），也可以按处方名、预设药方名搜
- 保存时：复用的不是预设药方 → 提醒「存成预设药方？」，可以起个名字；复用的是预设药方 → 不提醒

**要想清楚的**

1. 病人账号（家庭）要不要也有？（比如家里常煎的方子）
2. 预设药方要不要能编辑？编辑后，以前从它开出的处方不受影响（处方是复制出来的）
3. 搜索是在开方页上做一个弹窗，还是单独的页面

## IDEA-4 · 平台管理员数据看板（Admin Analytics Dashboard）

**Hao 的原话（整理）**

- 一个集中的管理员看板，看整个平台的使用情况、用户活动、药方统计
- 指标举例：每个用户建了多少张处方、用过多少种药材、哪些药材用得最多、哪些药材组合最常见、处方总数和趋势
- 不只是统计，还希望从数据里发现规律：使用习惯、异常操作、潜在的 bug、值得优化的功能
- **只允许平台 Owner / Developer 用专门的管理员账号访问**：不开放注册，普通用户不能自己获得管理员权限；管理员账号在系统内部预先配置，**后端验证权限**，不只是隐藏前端页面
- 涉及病人个人信息的数据尽量**匿名化或只给汇总**

**初步设计方向**

- 管理员名单：新表 `platform_admins`，和药材审核人（`monograph_reviewers`）一样，只能用 SQL 加，不写进 migration，App 里没有任何入口能改
- 页面布局里检查管理员身份，非管理员看到 404（和核对页一样）
- **数据库层面限制**：管理员账号也**不能**直接读其他药柜的表（RLS 不开后门）。看板的数据全部来自 `security definer` 的统计函数，函数里先检查调用人是管理员，并且**只返回汇总数字**（按用户、按药材、按天的计数），不返回病人姓名、电话、处方原文
- 用户在看板上用编号或邮箱显示（邮箱是我们自己的测试账号和医生，不是病人）；病人只出现在计数里
- 「药材组合」统计只统计成对出现的次数，不能反推出某个病人
- 异常操作和 bug 的线索可以接 IDEA-5 的错误记录

**要想清楚的**

1. 先要哪几个图表？（建议：每周新处方数、活跃用户、用得最多的 20 味药、常见药对）
2. 少于几个人的分组不显示（避免小样本能认出具体的人）？
3. 隐私：线上数据在美国区域，病人同意书还没定（0009 §6）。看板只给汇总，但仍然要在同意书里写明「平台会做匿名统计」（IDEA-6）

## IDEA-5 · 应用内 Bug 反馈与监控（Bug Reporting & Monitoring）

> **2026-11-10 第一阶段已实现**（悬浮按钮、存数据库、脱敏；Slack 接口写好但默认不发）：见 [`docs/design/0014-bug-reports.md`](design/0014-bug-reports.md)。下面是当时的想法，和最后做的不一样的地方以 0014 为准。

**Hao 的原话（整理）**

- **每个页面右下角一个悬浮的 Bug Report 按钮**，像常见的聊天机器人浮窗；点开填写问题描述、提交
- 除了用户写的内容，自动收集：当前页面、页面截图、最近的操作记录、时间，以及能拿到的应用日志和错误信息
- 统一存进数据库的专用表（或 schema），方便管理员查看、筛选、跟踪
- 应用在 **Vercel 免费 Hobby 计划**上，日志保存时间很短，所以提交时**同步保存相关的诊断日志**，免得重要信息丢掉
- 第二阶段：集成 **Slack 通知**，新报告自动发到指定频道，带问题摘要、时间和报告链接
- 截图、操作记录、日志**不能包含病人敏感信息、密码和其他凭证**，要过滤或脱敏

**初步设计方向**

- 表 `bug_reports`：提交人、药柜、页面路径、描述、浏览器信息、App 版本（部署的 commit）、最近操作（只记「点了哪个按钮、去了哪个页面」，不记输入的内容）、最近的前端错误、服务器端错误（按请求 ID 关联）、状态（新 / 处理中 / 已修 / 不修）。只有提交人能看到自己的报告，管理员通过 IDEA-4 的后台看
- 截图：存在私有 storage。**截图前把页面上的输入框、病人姓名、电话遮住**（页面上给这些元素加统一的标记，截图时替换成色块）；提交前让用户看一眼截图，可以选择不附截图
- 前端错误（未处理的异常、请求失败）平时先记在浏览器内存里，提交报告时一起带上；服务器端错误写进一张错误表（只保留最近 30 天），不依赖 Vercel 的日志
- 也可以考虑用 Sentry 之类的现成服务（有免费额度）收集错误，自己只做反馈按钮。要比较：数据存在别人那里（隐私）vs 自己做的工作量
- Slack：用 Incoming Webhook，地址放在环境变量里；消息里**只放编号、页面、时间和报告链接**，不放描述原文（描述里用户可能写了病人名字）

**要想清楚的**

1. 悬浮按钮在手机上会挡住底部的按钮（比如开方页的「保存」），位置和大小要设计
2. 截图怎么做：浏览器里把页面画成图片（不需要用户授权，但不完全准确）vs 浏览器的屏幕共享接口（准确，但每次都要用户点允许）
3. 病人账号和医生账号都显示按钮吗？

## IDEA-6 · 注册时的隐私同意书

**Hao 的决定（2026-11-07）**：注册时加一份同意书。现在只是给李医生用的试用版，规模还小；**正式开放给其他用户和医生之前**再做。

**要包括的**（来自 0009 §6 和 IDEA-4）

- 收集哪些数据、存在哪里（现在是 Supabase 美国区域；原计划是加拿大，换区域也在正式上线前做）
- 病人信息怎么用：只给本药柜的成员看；平台只做匿名的汇总统计（IDEA-4）；Bug 反馈会带上脱敏后的诊断信息（IDEA-5）
- 数据保留多久、怎么删除自己的账号和数据
- AI 拍照识别：照片会发给模型服务商做转录（OpenRouter），不做用药建议

**要想清楚的**

1. 医生账号替病人存病历：病人本人的同意怎么记录（医生线下拿同意书？App 里给病人建档时勾选「已取得同意」？）
2. 同意书改了以后，已注册的用户要不要重新同意
3. 加拿大的隐私法规（PIPEDA、各省的医疗信息法规）具体要求什么，可能要请懂法律的人看
