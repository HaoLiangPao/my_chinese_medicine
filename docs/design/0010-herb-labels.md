## 1. 目标

1. **药材资料**：每味药的来源、性味、归经、传统用途、炮制、道地产区、选品、毒性和使用注意、保存。全站共用一份，在药材详情页显示。
2. **药材标签（4×6 英寸）**：每味药打印一次，贴在药罐上。换批次不用重印。底部二维码打开公开的药材介绍页。
3. **批次标签（4×2 英寸）**：每次进货打印一张，贴在药材标签下面：批号、产地、净重、（可选）购自、购入日期、分装日期、建议用完。
4. **药材详情页**（`/herbs/[id]`）按设计稿重排：照片和性味 → 库存 → 药材资料 → 批次资料 → 用在哪些方子、比价。
5. **公开药材介绍页**：扫二维码打开，不用登录，只有药材资料。

不做：
- 用量 / 剂量。药材资料里**不写用量**，也不写针对某个人的用药建议（CLAUDE.md：AI 只做转录和科普）。
- 让用户在 App 里编辑药材资料（见 §2）。

## 3. 数据模型

### 3.1 药材资料：新表 `herb_monographs`

全站一份，一味药一行。第一次用 migration 从 JSON 导入；之后只有审核人能在核对页里改（§3.2），每次修改都留记录。

```sql
create table public.herb_monographs (
  herb_id        uuid primary key references public.herbs(id) on delete cascade,
  latin_name     text,                 -- 药材拉丁名，如 Ophiopogonis Radix；炮制品可空（显示原药材的）
  source         text,                 -- 来源（基原）：百合科植物麦冬的干燥块根
  flavors        text[] not null,      -- 味：{甘,微苦}
  nature         text not null,        -- 性：微寒
  meridians      text[] not null,      -- 归经：{心,肺,胃}
  traditional_use text not null,       -- 传统用途（功能），不写主治和用量
  processing     text,                 -- 炮制
  regions        text,                 -- 道地产区
  quality        text,                 -- 选品
  toxicity       text not null check (toxicity in ('none', 'minor', 'toxic', 'severe')),  -- 无毒 / 小毒 / 有毒 / 大毒
  cautions       text,                 -- 使用注意（传统记载的慎用、忌用、配伍禁忌）
  storage        text,                 -- 保存
  reference      text not null,        -- 依据：《中国药典》2020 年版一部 / 《中药学》教材
  status         text not null default 'draft' check (status in ('draft', 'reviewed')),
  reviewed_by    text,                 -- 审核人，如「李医生」
  reviewed_at    date,
  check ((status = 'reviewed') = (reviewed_by is not null and reviewed_at is not null))
);
```

- 炮制品（`herbs.base_herb_id` 不为空）有自己的一行时用自己的；没有就显示原药材的，并注明「资料同原药材」。
- RLS：
  - `authenticated`：能读全部（草稿也能看到，页面上标「草稿 · 待审核」）
  - `anon`：只能读 `status = 'reviewed'` 的（公开介绍页）
  - 不能直接 insert / update / delete；审核人通过 `review_herb_monograph()` 函数改（§3.2）

**显示规则**（未审核的 AI 草稿不能给病人看）：

| 地方 | 草稿 | 已审核 |
|---|---|---|
| 登录后的药材详情页 | 显示，标「草稿 · 待审核」 | 显示，底部「内容审核：李医生 · 2026-11」 |
| 药材标签打印 | **不能打印**，按钮旁提示「资料还没审核」 | 可以打印 |
| 公开介绍页（二维码） | 显示「这味药的资料正在整理中」 | 显示 |

### 3.2 资料的录入和审核流程（2026-11-07 定：App 里做核对页）

**录入**：`supabase/data/herb-monographs.json` 是初稿。`scripts/gen-herb-monographs.mjs` 读它，生成一个 migration 导入（`on conflict (herb_id) do nothing`：已经有的不覆盖，免得冲掉审核过的内容）。导入以后，**数据库是正式来源**，JSON 只做初稿和备份（定期用脚本从数据库导出一份回来，方便在 git 里看改了什么）。

单元测试 `herb-monographs.test.ts` 检查 JSON（已有）：每味药都在目录里、炮制品的 `base` 对得上、性味归经写法合法、不出现「数字 + 克」、审核字段一致。

**审核人**：新表 `monograph_reviewers (user_id, display_name)`，管理员用 SQL 加（例如李医生的账号，`display_name = '李医生'`）。不在 migration 里写邮箱。

**核对页** `/review/herbs`（只有审核人能打开，别人 404）：

- 列表：药名、状态（草稿 / 已审核）、有没有 `check` 标记；可以只看「待审核」「要重点核对」
- 点进一味药：每个字段都能改；`check` 的内容显示在最上面
- 三个按钮：
  - **通过**：保存修改，状态改成已审核，记审核人（`display_name`）和日期
  - **先存着**：只保存修改，还是草稿
  - **有问题**：写一句备注，留给我们处理
- 改完自动跳到下一味待审核的药
- 手机上也能用（李医生可能用手机看）

**修改记录**：新表 `herb_monograph_revisions`（`herb_id`、改之前和改之后的内容 jsonb、谁、什么时候、动作、备注），由 `review_herb_monograph()` 写，只能追加，不能改也不能删。审核过的内容再改，状态退回草稿，要重新通过。

**函数** `review_herb_monograph(herb_id, content jsonb, action text, note text)`：检查调用人在 `monograph_reviewers` 里；同样做 JSON 测试里的格式检查（性、味、归经、不出现用量）；写 `herb_monographs` 和 `herb_monograph_revisions`。

### 3.3 批次：采购明细加三列

现在系统里没有「批次」。一次采购里的一味药（`purchase_items` 的一行）就是一个批次。

```sql
alter table public.purchase_items
  add column origin       text,   -- 产地：中国 · 浙江
  add column lot_no       text,   -- 批号（自动生成，见下）
  add column supplier_lot text,   -- 供应商批号（可选，照包装抄）
  add column packed_on    date;   -- 分装日期（可选）
```

- 都是可以为空的列，旧代码不受影响（先扩展、后收缩）。
- **批号**：`<药名拼音首字母>-<购入年月 YYMM>-<序号>`，如麦冬 2026 年 11 月第一批 → `MD-2611-01`。序号按「药柜 + 首字母 + 年月」递增（黄芪、黄芩都是 HQ，序号不会撞）。插入时由触发器生成；已有的采购在 migration 里按购入日期回填。需要升级测试（`supabase/tests/upgrade/<migration>.sql`）。
- **建议用完**：分装日期（没有就用购入日期）+ 12 个月。先写成常量，以后需要再按药材区分。
- **在用 / 已用完**：库存是流水账，不按批次记扣减。显示时按「先进先出」推算：从最新的一批往回累加克数，直到超过当前库存，这些批次是「在用」，更早的是「已用完」。纯计算放在 `src/lib/batches.ts`，写单元测试。不加「剩余克数」字段（CLAUDE.md）。
- 进货表单每行加「产地」「供应商批号」「分装日期」，放在「更多」里收起来，不影响现在的录入速度。

### 3.4 药材目录要补的药（审核前先做）

草稿里有 6 处「要确认是哪一种」。其中 5 处是**不同的药**（药典里是分开的条目，植物或者部位不同，功效也不完全一样），1 处是**炮制品**：

| 现在目录里 | 另一种 | 关系 | 打算 |
|---|---|---|---|
| 黄柏（按川黄柏写） | 关黄柏 | 不同的药：黄皮树 vs 黄檗的树皮 | 加「关黄柏」 |
| 藿香（按广藿香写） | 土藿香 | 不同的药：广藿香 vs 藿香，药典只收广藿香 | 加别名「广藿香」→ 藿香；土藿香等李医生说用不用 |
| 牛膝（按怀牛膝写） | 川牛膝 | 不同的药：两种不同的植物 | 加「川牛膝」；已有别名「怀牛膝」 |
| 沙参（按北沙参写） | 南沙参 | 不同的药：伞形科 vs 桔梗科 | 加「北沙参」「南沙参」；「沙参」怎么处理问李医生（她平时写「沙参」指哪一种） |
| 石斛 | 铁皮石斛 | 不同的药：药典单列 | 加「铁皮石斛」 |
| 何首乌（生） | 制何首乌 | 炮制品 | 加「制何首乌」，`base_herb_id` 指向何首乌，别名「制首乌」 |

目录在种子文件里，加新药是 seed 的改动（`on conflict do nothing`，可以重复执行），已有药方不受影响。

### 3.5 照片（最后一个 PR）

两种照片：

| | 默认照片 | 本罐照片 |
|---|---|---|
| 谁提供 | 我们找的，全站一份 | 用户自己拍、上传 |
| 存在哪里 | 公开的 storage bucket；`herb_monographs` 加 `photo_path`、`photo_credit`（作者）、`photo_license`、`photo_source_url` | 私有 storage（按药柜隔离），`pantry_settings` 加 `photo_path` |
| 在哪里显示 | 公开介绍页；药材标签和详情页在没有本罐照片时用它 | 只在自己药柜的详情页和自己打印的标签上 |

默认照片**必须能合法使用**：只用公有领域或 CC BY / CC BY-SA 授权的图（比如 Wikimedia Commons），记下作者、授权和来源网址。公开页在照片下面写出处；标签上空间小，写「图：作者 / 授权」一行小字。没有合适授权的照片就先不放，用文字占位。

## 4. 页面

### 4.1 药材详情页 `/herbs/[id]`（登录后）

从上到下：

1. 照片（没有就不占位）、药名、拼音、拉丁名、别名；性味、归经、毒性做成小标签
2. 库存：剩余克数、提醒线进度条、「记采购 / 记进货」「称重校准」按钮（跳到已有的页面，不在这里另做表单）
3. 药材资料 + 「打印药材标签」；底部审核人或「草稿 · 待审核」
4. 批次资料：在用的批次（产地、购自、购入、净重、单价、建议用完）+ 历史批次；每批「打印批次标签」
5. 用在哪些方子（已有）、比价（只有病人账号；医生账号没有比价，见 0008）

用语按账号类型（`terms.ts`）：采购 / 进货、药方 / 处方、副 / 剂。

### 4.2 公开介绍页 `/learn/herbs/[id]`

- 放在「学堂」下面，本来就不用登录。
- 只有药材资料（和药材标签一致）+ 「仅为中药知识介绍，不作用药建议；请在中医师指导下使用」。
- 没有库存、价格、方子、诊所名称以外的任何药柜数据。
- 地址用 `herbs.id`（不会变），二维码印上去以后一直有效。

### 4.3 打印

- `/print/herb/[id]`：药材标签，4×6 英寸
- `/print/batch/[purchaseItemId]?store=1`：批次标签，4×2 英寸；`store=1` 才印「购自」，打印前有勾选框
- 用浏览器打印：`@page { size: 4in 6in; margin: 0 }`，页面只有标签本身。4×6 是常见的热敏标签纸尺寸，标签打印机（如 Rollo、Zebra）可以直接用；普通打印机打在 A4 / Letter 上再剪
- 二维码在服务器端生成 SVG（加一个依赖：`qrcode`），内容是公开介绍页的完整网址
- 标签抬头用药柜名称（诊所名或「我们家」），打印前可以改
- 底部固定文字：「中药饮片，请在中医师指导下使用 · 本标签不作疗效声明」

## 7. 还要定的

1. 批号格式。`MD-2611-01` 是照设计稿上的例子写的（拼音首字母 + 年月 + 序号），不是行业标准。饮片厂自己的批号多是纯数字（比如年月日加流水号），这个我们存在「供应商批号」里，照包装抄。内部批号只是为了在药柜里区分批次，可以换成别的格式
2. 「沙参」在李医生的处方里一般指北沙参还是南沙参？（§3.4）
