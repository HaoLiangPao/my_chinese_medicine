## 1. 目标和范围

平台 Owner / Developer（现在只有 Hao）想知道整个平台用得怎么样：有多少账号和药柜、处方建得多不多、谁在用、哪些药材和组合最常用；还要在同一个地方处理用户的 Bug 反馈（IDEA-5）。

前提（IDEA-4 的硬性要求）：
- 只有预先配置的管理员能看，**后端**验证，不是只把入口藏起来
- 管理员**不能**因此读到任何一个药柜的原始数据：RLS 不开后门
- 只给汇总数字；**病人只出现在计数里**；不能从数字反推出某个病人

第一版做：
- 管理员名单 `platform_admins`（§3）
- 看板用的数据库函数（§4）
- 看板 `/admin`：总览、Bugs、医生、病人四个 tab，医生和病人账号有详情页（§6）

**2026-11-12 Hao 看了第一版截图后定的**（PR #29 里改）：
- 看板不要 App 的导航，自己一套 tab；Bug 反馈列表放进来
- 时间可以**任意选起止日期**（原来只能选整月），药材和组合也一样；接受由此带来的「相减」风险（§5.3）
- 药材和组合的 **5 位病人门槛保留**
- 药材显示**使用量**（克数），可以选 Top 10 / 20 / 30 / 40
- 医生详情：病人数、处方数、库存消耗
- 病人 tab：**只看病人账号的汇总数字**，不显示用了哪些药，不碰诊所的病人档案
- 图表要有纵轴
- 学堂的使用情况不放这里，以后用外部的 observability 工具看

## 2. 威胁模型：防的是什么

| 防 | 不防 |
|---|---|
| 普通账号（病人、医生）打开看板、直接调这些函数 | Hao 本人在 Supabase 后台直接查库（他本来就有超级用户权限，看板不改变这一点） |
| 管理员账号被盗 / 看板截图被转发：拿到的只有数字，没有病人姓名、电话、处方原文、备注 | 有意拿两个重叠的时间段相减，算出被门槛隐藏的药材（§5.3，Hao 接受） |
| 选很短的时间段（比如一天），直接看到某一次就诊开了什么药 | |

所以看板的隐私设计目标是：**这个入口本身**不会顺手把某个病人的用药摆出来。

## 3. 权限模型

### 3.1 `platform_admins`

```sql
create table public.platform_admins (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  note       text check (char_length(note) <= 100),
  created_at timestamptz not null default now()
);
```

- 和 `monograph_reviewers`（0010 §3.2）一样：**只能用 SQL 加人**；migration 里不写任何账号；App 里没有任何入口能改
- 比 `monograph_reviewers` 更严：开 RLS 但**一条 policy 都没有**，并且收回 `anon`、`authenticated` 的全部权限（读也不行）。客户端只能通过 `is_platform_admin()` 知道「自己是不是」，不能列出有谁
- 账号删了，管理员身份跟着删（`on delete cascade`）

线上加管理员（Hao 在 Supabase 后台 SQL Editor 执行，邮箱换成自己的管理员账号）：

```sql
insert into public.platform_admins (user_id, note)
select id, '平台管理员' from auth.users where email = '<管理员账号的邮箱>';
```

去掉：`delete from public.platform_admins where user_id = (select id from auth.users where email = '<邮箱>');`

管理员就是一个普通的病人或医生账号，**额外**在这张表里；账号类型仍然只有病人和医生两种（0008）。

### 3.2 统计函数的检查

每个统计函数都是 `security definer`（以函数所有者身份执行，才能跨药柜汇总），第一行先调 `admin_require()`：

```sql
if not exists (select 1 from public.platform_admins where user_id = auth.uid()) then
  raise exception '没有权限' using errcode = '42501';
end if;
```

- 不是管理员：报错，**一行都不返回**
- 未登录（`anon`）：连 `execute` 权限都没有
- `admin_require()`、`admin_window()` 这些内部函数谁都不能直接调用（收回 `execute`；`security definer` 函数里调用时用的是所有者的权限）
- 唯一的写操作 `admin_set_bug_status` 也一样：先 `admin_require()`，只能改 `bug_reports.status`

### 3.3 RLS 不开后门

不改任何已有表的 policy，也不在 `is_member()` 里加「管理员例外」。管理员账号直接 `select * from prescriptions` 只看到自己药柜的（SQL 测试覆盖）。

### 3.4 页面

`/admin` 下所有页面（总览、Bugs、医生、病人和两个详情页）的 layout 在服务器端调 `is_platform_admin()`，不是 `true` 就 `notFound()`（和核对页 `/review` 一样）。Next 的 layout 和 page 是同时渲染的，所以每个页面、每个 server action 在调函数之前**再查一次**（`requireAdmin()`），非管理员根本不会去调。所以：
- 没登录 → 跳登录页（`proxy.ts`，所有内部页面都一样，不暴露 `/admin` 存在不存在）
- 登录了但不是管理员 → 和不存在的地址一样的 404
- 就算页面的检查被绕过，统计函数自己还会拒绝（两层）

App 的导航里不放入口，管理员自己记住地址。检查通过以后，看板把 App 的导航（药方、药柜……）藏起来，换成自己的 tab（§6）。

## 4. 函数

时间都按 **处方的 `created_at`**（录进系统的时间 = 平台的使用情况；配药按 `decocted_at`，库存消耗按流水的 `occurred_at`），按 **多伦多时间（America/Toronto）** 算日期，和 App 里的「今天」一致（李医生在多伦多）。

时间段 `p_from`、`p_to` 是日期，**两头都包含**，`null` = 不限。1990 年以前、2100 年以后、`infinity` 都不接受（`infinity` 会让趋势一直生成日期）；开始晚于结束报错。

### 4.1 总览

| 函数 | 返回 | 说明 |
|---|---|---|
| `is_platform_admin()` | `boolean` | 只说「我是不是」，页面用 |
| `admin_overview(p_from, p_to)` | 一行：账号数（病人 / 医生 / 没选类型）、药柜数（家庭 / 诊所）、病人档案总数、处方总数、这段时间的处方数和建过处方的账号数 | 账号、药柜、病人档案是**当前总数**，不按时间段 |
| `admin_prescription_trend(p_bucket, p_from, p_to, p_user)` | `(bucket_start, prescriptions, bucket)` | 每天 / 每周（周一开始）/ 每月几张，没有处方的也有 0。`auto`：62 天以内按天，两年以内按周，再长按月。不限开始日期时从第一张处方开始。最多 400 个点。`p_user` 给了就只数这个账号自己的药柜（详情页用） |
| `admin_user_activity(p_from, p_to)` | 每个这段时间建过处方的账号一行：编号、`email`（**只有医生账号有**）、类型、处方数、药材种数、最近一次、是不是自己 | 按 `prescriptions.created_by`。编号按第一次加入药柜的时间排 |
| `admin_top_herbs(p_from, p_to, p_limit, p_order)` | `(herb_name, prescriptions, total_grams, other_herbs)` | 常用药材，`p_order` = `grams`（累计克数 = 每副克数 × 剂数）或 `rx`（处方张数），最多 `p_limit` 行（1–50）。不到门槛的合成最后一行「其他」：名字、张数、克数为 `null`，`other_herbs` = 合进去了几味 |
| `admin_top_pairs(p_from, p_to, p_limit)` | `(herb_a, herb_b, prescriptions, other_pairs)` | 同一张处方里成对出现的两味药，同样的门槛和「其他」行 |

### 4.2 医生

| 函数 | 返回 | 说明 |
|---|---|---|
| `admin_doctors(p_from, p_to, p_user)` | 每个医生账号一行：编号、邮箱、病人档案数（总数 / 这段时间新建 / 这段时间看过）、处方数（这段时间 / 总数）、配药次数、库存消耗克数、最近一次处方 | 「医生的药柜」= 他是成员、并且是诊所的药柜。病人**只有数量**。`p_user` 给了就只返回这一个（详情页） |
| `admin_doctor_consumption(p_user, p_from, p_to, p_limit)` | `(herb_name, consumed_grams, other_herbs)` | 这个医生的诊所逐味的库存消耗（`inventory_txns` 里 `consume` 的克数）。**同样的 5 位病人门槛**：病人从这笔配药对应的处方来 |

### 4.3 病人账号

| 函数 | 返回 | 说明 |
|---|---|---|
| `admin_patient_accounts(p_from, p_to, p_user)` | 每个病人账号一行：编号、家里几个人、处方数（这段时间 / 总数）、用过几种药、煎药次数、录药方的天数、最近一次、是不是自己 | **只有数字**：没有邮箱，没有用了哪些药（Hao 2026-11-12 定的）。诊所里的病人档案不在这里，只在医生那里算数量 |

### 4.4 Bug 反馈（IDEA-5）

| 函数 | 返回 | 说明 |
|---|---|---|
| `admin_bug_reports(p_status, p_limit)` | 每条反馈：时间、状态、提交人编号和类型（医生加邮箱）、页面路径、描述、浏览器、屏幕、版本、最近操作、前端错误 | 描述是用户自己写的，可能提到病人；管理员处理反馈本来就要读描述（0014）。提交人和其他地方一样，病人账号只有编号 |
| `admin_set_bug_status(p_id, p_status)` | — | 新 / 处理中 / 已修 / 不修。看板里唯一的写操作 |

## 5. 防止反推

### 5.1 「几位病人」怎么数

一味药（或一对药）「出现在几位病人的处方里」，分两组数，**取较大的那组，不相加**：
- 诊所组：不同的 `patient_id` 有几个
- 家庭组：没挂病人的处方（家庭处方，或者诊所里没挂病人的）来自几个不同的药柜；一个家庭药柜里一家人算一个

为什么不相加：同一个人常常两边都有。李医生给他开了方（诊所里一个病人），他又用自己的病人账号把这张方录进家里（一个家庭药柜）。相加的话这个人会算两次，「5 个病人」实际可能只有 3 个人（第 1 轮审核指出）。分组取较大的，在「每个人最多一个诊所档案、一个家庭」的前提下不会重复计算。将来一个人在好几个诊所都有档案时还会重复，那时要提高门槛或者按账号关联去重。

医生的逐味库存消耗也一样，病人从配药对应的处方来。

### 5.2 门槛：5 位病人

一味药（或一对药）**至少出现在 5 位不同病人的处方里**，才单独显示；否则合进「其他」，只说合进去了几味 / 几对。Top 40 不一定有 40 行。

- 数的是**病人**，不是处方：同一个病人开了 6 次白术，还是只有 1 位病人，不显示（测试里有这种情况）
- 为什么是 5：统计发布里常用的「小格子」门槛是 5～11（不少统计机构用 5，美国 CMS 用 11）。现在平台上只有李医生一个真实医生、病人几十个；门槛太高看板就什么都没有，太低（1、2）就等于把某个病人的用药列出来。以后病人多了可以提高，只改一个常量（`admin_min_subjects()`）
- 为什么只有药材和组合有门槛：只有它们带着「开了什么」。处方数、每天几张、账号数只能看出「有人看过病」

### 5.3 任意时间段和「相减」（Hao 接受的风险）

第一版只接受整月、而且药材只按单月给，因为两个**重叠**的时间段可以相减：比如「1–3 月」减「2–3 月」= 1 月，被门槛藏起来的药材就算出来了（第 1 轮审核复现过：再对上账号列表里那个月只有某个病人账号建过处方，就知道他开了什么）。

2026-11-12 Hao 决定要任意起止日期（时间长了按月份的按钮放不下，也想看任意一段），接受这个风险。理由：看板账号只有 Hao，他本来就能在 Supabase 后台看到全部数据。门槛仍然保留，所以：
- **挡得住**：选一天、一小时这种短时间段，直接看到某一次就诊开了什么药——单独显示的每味药仍然至少有 5 位病人
- **挡不住**：有意拿两个重叠的时间段相减

以后如果看板开放给 Hao 以外的人，要重新考虑：改回不重叠的时间段（整月），或者给数字加噪声。

### 5.4 其他数字为什么不设门槛

- **处方趋势**、**每个账号的处方数和药材种数**、**医生的病人数和处方数**、**病人账号的数字**：只有数量，不带开了什么。病人账号不显示邮箱，只显示编号
- **病人档案总数**：一个数字

这几项如果以后觉得也要保护，可以改成小于 5 显示「<5」。**需要 Hao 决定**（见 PR）。

## 6. 页面

检查通过以后，App 的导航藏起来（`<style>` 隐藏 `[data-app-header]`，只在管理员看到的 layout 里输出），换成看板自己的 tab：**总览 · Bugs · 医生 · 病人**。切换 tab 时带上选好的时间段（Bugs 不按时间段看）。

- **时间段**（总览、医生、病人和详情页）：快捷按钮（全部、最近 7 / 30 / 90 天、本月、上个月、今年）+ 任意起止日期（GET 表单，地址栏 `?from=2026-02-01&to=2026-02-28`）。不合法的日期当成不限，开始晚于结束就对调
- **总览**：概况卡片；处方趋势柱状图（有纵轴刻度和网格线，粒度自动）；这段时间建过处方的账号（医生点进医生详情，病人账号点进病人详情）；常用药材（Top 10 / 20 / 30 / 40，按用量 / 按张数）；常见组合
- **Bugs**：按状态筛选（全部 / 新 / 处理中 / 已修 / 不修，带数量）；每条显示状态、页面、时间、描述、提交人（点进账号详情）、可以展开的诊断信息；改状态
- **医生**：列表 → 详情：病人档案数（总数、新建、看过）、处方、配药、库存消耗、趋势、逐味库存消耗（Top N，过门槛）
- **病人**：病人账号列表 → 详情：药方数、用过几种药（不显示是哪些）、煎药次数、录药方的天数、趋势
- 不加图表库：柱状图和横条都是 CSS 的 `div`，每根柱子带 `data-count` 和读屏用的 `aria-label`
- 手机 390px：整页不横向溢出（E2E 检查）
