## 1. 煎药记录（decoctions）

### 为什么需要

MVP1 第一版只有「按处方原量扣库存」。实际煎药时经常和处方不完全一样：

- 抓药时手一抖，黄芪多了 5 g
- 某味药这次没放（家里没了，或者医生说可以不放）
- 临时加了处方外的东西（几片生姜、一点陈皮）
- 记错了，要撤销

### 数据模型

```
decoctions        一次煎药：哪张药方、几副、什么时候、备注
decoction_items   每味药：planned_grams（处方量 = 每副 × 副数）、actual_grams（实际总量）
inventory_txns    + decoction_id：每味实际用量 > 0 的药写一条扣减流水
```

- `record_decoction(药方, 副数, 实际用量 JSON, 备注)`：没列出的药按处方量，列出的按实际，处方外的 planned = 0。
- 撤销 = 删除 decoction，流水级联删除，库存自动恢复。
- 删除药方：煎药记录保留（`prescription_id` 置空），已扣的库存不回滚（药确实用掉了）。
- `v_decoction_variance`：每次煎药每味药的差额和状态（exact / over / under / omitted / extra）。
- 库存允许变成负数：说明账上没记的药被用了，提醒去补货或盘点。

### 界面

药方详情页「煎药」：默认按处方量，每味药一个「实际用量」输入框（填的是这次总量）。改过的标黄。可以加处方外的药。下面是煎药历史，只列出和处方不一样的地方，每条可撤销。

## 2. 测试体系

| 层 | 工具 | 跑法 | 覆盖 |
|---|---|---|---|
| 单元测试 | Vitest | `cd web && npm test` | `src/lib/` 下的纯函数：合并、单位换算、可配副数、煎药差额、成本汇总、比价 |
| SQL 测试 | psql + 断言函数 | `scripts/test-db.sh` | 每个 `supabase/tests/*_test.sql` 在全新数据库里跑：库存、统计、煎药边界、约束、各表 RLS、邀请与家人共享、比价 |
| E2E | Playwright | `scripts/e2e.sh` | 真实浏览器 → Next.js → 本地 Supabase-lite，全程操作界面 |
| 全部 | — | `scripts/test-all.sh` | 以上所有，按顺序跑 |

### 本地 Supabase-lite

官方的 `supabase start` 依赖 Docker。为了在没有 Docker 的环境（包括这次开发用的云端环境）也能跑完整 E2E，`scripts/local-stack.sh` 用官方二进制拼了一套：

| 组件 | 来源 | 端口 |
|---|---|---|
| Postgres | 本机安装的 PostgreSQL 16 | 54322 |
| Supabase Auth（GoTrue） | GitHub release 二进制 v2.180.0 | 9999 |
| PostgREST | GitHub release 二进制 v12.2.3 | 3001 |
| 网关（相当于 Kong） | `scripts/local-gateway.mjs` | 54321 |

角色（anon / authenticated / service_role / authenticator）按 Supabase 的默认设置建（`supabase/local/bootstrap.sql`），所以 RLS 的行为和线上一致。

**已知差异**：Storage 是一个极简的文件存储（`.local/storage`），只实现了上传、删除、签名链接，**不执行 storage 的 RLS**。照片的权限隔离要等上了真实 Supabase 再验证（见 §5）。

### E2E 场景

`web/e2e/fixtures/scenario.ts` 是场景数据和期望值：

- **10 张药方**：四君子汤、补中益气汤、八珍汤、归脾汤、逍遥散、六味地黄汤、生脉散、玉屏风散、小柴胡汤、酸枣仁汤。剂量取《方剂学》现代常用量（资料由一个便宜的模型收集，我对照教材核对过，归脾汤按教材修正了）。**只用作测试数据，不是用药建议。**
  - 录入时故意用了别名（北芪、熟地、山萸肉、丹皮、炒枣仁）
  - 目录里没有的药（茯神、煨姜）会自动新建
  - 同一味药录两行（八珍汤的当归）会合并；有小数克数、有「后下」脚注
- **5 家虚构药行**：价格按 `price-ranges.json` 的区间加上每家店的系数生成。这些区间大多是估算，只有 3 味药找到了真实标价。
  - 黄芪三家都买过；同一张单子里重复的行会合并；人参只少量买了一次；大枣是赠品（0 元）
  - 有几味药从没买过（防风、升麻、远志等）
- **9 次煎药**：
  1. 按处方煎（人参不够，库存变负）
  2. 黄芪多抓 5 g
  3. 丹皮没放
  4. 多加姜（姜在处方里，所以叠加）+ 加陈皮（处方外）
  5. 防风从没买过
  6. 酸枣仁汤煎两次，第二次川芎少放
  7. 煎完后删除这张药方（生脉散）
  8. 记错了，撤销（八珍汤）
- **校准**：称重发现黄芪比账上少 3 g。

最后对账：

- 数据库里每味药的库存，要和 `expectedStock()` 独立算出的账本完全一致
- 药柜页面上每一张卡片的数字也要一致
- 药材统计（出现次数、累计用量）和比价、成本，都由测试独立计算期望值
- 家人看到的是同一个药柜，陌生人什么都看不到

另外 `isolated.spec.ts` 覆盖登录/权限、拍照识别（用假的 OpenRouter 服务，`e2e/mock-openrouter.mjs`，包括第一个模型失败后换第二个）、表单校验、补货提醒；`mobile.spec.ts` 在手机尺寸下检查所有页面没有横向溢出。

## 3. 测试发现并修复的问题

| 问题 | 怎么发现的 | 修复 |
|---|---|---|
| 把家人拉进来时，对方只有店铺/盘点数据的 workspace 会被当成空的删掉 | SQL 测试 | migration 0004：`workspace_is_empty()` 检查所有业务表（后来整个「拉人」改成邀请制，见 0004） |
| 改采购日期后，库存流水的时间没跟着改 | 写 SQL 测试时发现 | migration 0003：触发器同步 |
| 手动录入别名（北芪）时没保存原文 | E2E | 原文总是存进 `raw_name` |
| 删除药方后跳回列表，还能看到被删的药方 | E2E | 关闭 Cache Components（见 §4） |
| 邀请家人时邮箱填错，整个页面报错 | 写 E2E 时发现 | 改成表单内提示 |
| 未登录调用识别接口，被重定向到登录页（API 应该返回 401） | E2E | proxy 对 `/api/*` 返回 401 JSON |
| 预渲染阶段读取当前时间报错 | E2E 日志 | `getContext()` 先调 `connection()` |
| 识别失败时已经上传的照片没挂到药方上 | 写 E2E 时发现 | 失败时仍保留照片 |
| 手机上表格里的数字和药名折行 | 手机截图 | 表格单元格不折行，表格在卡片内横向滚动 |

## 4. 决定：关闭 Next.js 16 的 Cache Components

Next.js 16 的模板默认开启 `cacheComponents` 和 `partialPrefetching`。开启后，客户端会把离开的页面藏起来保留（React `<Activity>`）。在这个 App 里，执行服务器端操作后 `redirect` 回之前访问过的页面时，显示的是旧内容：删除药方后列表里还在。`revalidatePath('/', 'layout')`、`refresh()`、换一个新 URL 都没有解决，刷新页面才正常。

关闭后问题消失。这个 App 每个页面都是登录用户自己的实时数据，本来就没有可以静态缓存的内容，Cache Components 对它没有收益。

E2E 里加了回归测试：

- 删除药方后跳回列表，不能看到已删除的药方
- 煎药后通过导航链接（客户端跳转，不刷新页面）看到的库存必须是最新的

Next.js 说下一个大版本会默认开启且不能关闭，到时候需要重新评估，这些回归测试会先报出来。

## 5. 还没覆盖到的

- **真实 Supabase 上的 Storage RLS**（本地存储是简化版）。上线后要手动验证：A 家的照片链接 B 家打不开。
- **真实模型的识别准确率**：E2E 用的是假模型。需要拿李医生的真实药方照片测一下，再调 prompt。
- **并发**：两个人同时编辑同一个药柜。目前只有追加式的流水，问题不大，但没有专门测。
