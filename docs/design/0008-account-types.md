## 1. 目标

1. **注册时选「我是病人」或「我是医生」**（数据库里还是 `household` / `clinic`，下文的「家庭」= 病人账号，「诊所」= 医生账号），之后不能自己改。家庭账号不能开诊所；诊所账号只用诊所。两种都要用的话，用另一个邮箱再注册一个账号。
2. 诊所账号的导航：开方、病人、处方、库存、进货、学堂。没有「比价」，`/prices` 也打不开。
3. 家庭账号打不开 `/clinic/*`。
4. **一个账号只有一个药柜，没有切换。** 病人账号接受家人邀请时，搬进对方的药柜；自己原来的药柜隐藏（数据不删），退出对方的药柜后回来。接受前弹窗说明。
5. 导航加自己画的 SVG 图标，项目之间有分隔线。
6. 诊所模式不再出现家庭用语（问题 5）：「家庭成员」「家里每个罐子」「盘点：家里原本就有的」「采购 / 进货」混用、「剂 / 副」混用。

不做：邀请成员的新功能（产品先定位成医生工具，见会话记录 §2）。家庭药柜已有的邀请功能保留不动；诊所的总览页**不显示**成员管理。

## 2. 数据模型

### 2.1 账号类型放在 `user_settings.account_kind`

```sql
alter table user_settings add column account_kind text check (account_kind in ('household', 'clinic'));
```

- `null` = 还没选（上线前注册的旧账号、刚注册还没选的）。
- 不新建 `profiles` 表：`user_settings` 本来就是每个用户一行，只能本人读、只能通过函数写，正好合适。
- 和 `workspaces.kind` 用同一组值，判断「同类型」就是 `w.kind = s.account_kind`。

### 2.2 函数

| 函数 | 变化 |
|---|---|
| `choose_account_kind(kind, clinic_name)` 新增 | 只能选一次（已经选过同一种 → 什么都不做；选过另一种 → 报错）。家庭：用自己已有的家庭药柜，没有就建「我们家」。诊所：用自己已有的诊所，没有就用 `clinic_name` 建一个（名字必填）。最后把当前药柜设成这个 |
| `current_context()` 新增 | 一次返回 `account_kind, workspace_id, workspace_name, workspace_kind`。没选类型时只返回 `account_kind = null`，**不建药柜**（新代码据此跳到选择页）。选了类型时：当前药柜不是同类型就换成第一个同类型的；一个都没有就建一个（家庭「我们家」，诊所「我的诊所」） |
| `ensure_default_workspace()` | 选了类型时只挑同类型的药柜；没选（`null`）时和原来一样（部署期间旧代码还在跑） |
| `my_workspaces()` | 选了类型时只返回当前药柜 |
| `set_active_workspace(ws)` | 选了类型以后不能切换：同类型的另一个药柜 →「一个账号只有一个药柜，不能切换」；另一种类型 →「不能切换到另一种类型的药柜」；设成当前的那个 → 什么都不变。旧代码（`null`）照常 |
| `create_clinic(name)` | 家庭账号 → 报错。旧代码要用，先保留，以后再收缩 |
| `my_invitations()` / `accept_invitation(inv)` | 只看到 / 只能接受同类型药柜的邀请；接受 = 搬进对方的药柜（当前药柜换成对方的，自己原来的空药柜删掉、有数据的隐藏） |

`is_member(ws)`：选了类型以后，**只有当前药柜**（`user_settings.active_workspace_id`，而且和账号同类型）算成员；另一种类型的、搬走前自己的药柜都不算。没选类型（`null`）时和原来一样。

「一个账号一个药柜」不加新字段：当前药柜就是那一个。接受邀请把当前药柜设成对方的；`leave_workspace` / `remove_member` 本来就会清空当前药柜，`ensure_default_workspace` 再选最早加入的同类型药柜，也就是自己原来的那个。RLS 规则本身不变，但都经过它，所以页面、写操作、照片、直接调 API 都一起挡住，不用每个查询各加过滤。

### 2.3 旧账号（两个测试账号都同时有家庭和诊所）

- 旧账号 `account_kind = null`，下次登录进入「选择账号类型」页。页面上说明：你现在同时有家庭药柜和诊所，选了以后另一种会**隐藏**，数据不删。
- 隐藏 = 不在列表里、切不过去，用旧链接或直接调 API 也读不到、改不了（`is_member` 返回 false）；成员关系和数据还在数据库里，管理员改回类型就能恢复。
- **不在 migration 里写测试账号的邮箱**。冒烟测试登录时如果遇到选择页，病人账号选「家庭」、诊所账号选「诊所」——合并后第一次冒烟测试就完成了迁移（hao-test 只留家庭，tina-test 只留诊所）。
- 改账号类型不提供自助入口；真要改，由管理员用 SQL 改 `user_settings.account_kind`。

### 2.4 部署顺序（先扩展、后收缩）

migration 先上线、旧代码还在跑时：旧代码不知道 `account_kind`，所有账号都是 `null`，所有函数都按原来的方式工作。新代码上线后才会让用户去选。`create_clinic`、`ensure_default_workspace` 留着，以后另开 migration 收缩。

## 3. 注册和选择

1. 注册表单加两个选项：**我是病人**（记自己和家人的药方、管家里的药柜）/ **我是医生**（给病人开方、管诊所的库存）。选医生时要填诊所名称。没选就点「注册」→ 选项自动展开，提示「请选择：你是病人还是医生」。
2. 注册成功且直接登录了（没开邮箱确认）→ 马上调 `choose_account_kind`。
3. 需要邮箱确认的话，选择写进 `user_metadata`；确认后第一次登录，选择页按它预选好。`user_metadata` 用户自己能改，所以只用来**预选**，真正生效以 `choose_account_kind` 为准。
4. `getContext()` 改用 `current_context()`（顺便少一次查询）；`account_kind` 是 `null` 就跳到 `/welcome`。

## 4. 页面

### 4.1 导航

| 家庭 | 诊所 |
|---|---|
| 药方 · 药柜 · 采购 · 比价 · 药材 · 学堂 | 开方 · 病人 · 处方 · 库存 · 进货 · 学堂 |

- 每项前面一个自己画的 SVG 图标（20px，`stroke="currentColor"`，跟随文字颜色），项目之间一条竖线分隔。
- 手机上导航横向滚动（和现在一样），不换行。

### 4.2 访问限制

| 地址 | 家庭账号 | 诊所账号 |
|---|---|---|
| `/clinic/*` | 找不到页面 | 正常 |
| `/prices` | 正常 | 找不到页面 |
| `/prescriptions/new` | 正常 | 转到 `/clinic/prescribe`（已有） |

原来 `/clinic/*` 里「先创建一个诊所」的表单、总览页的「我是医生：创建诊所」入口都去掉。

### 4.3 总览页

- 家庭：和现在一样（统计、录药方 / 拍照识别、记一笔采购、最近的药方、该补货了、家庭成员）。
- 诊所：统计「处方 / 库存药材 / 快用完」，按钮「＋ 开方」「＋ 记一笔进货」，「最近的处方」（带病人），「该进货了」。底部只有账号信息和退出登录，**没有成员管理**。
- 没有切换药柜的入口（一个账号一个药柜）。家庭的「收到的邀请」点「接受」前弹窗：以后只用对方的药柜，自己的隐藏、数据不删、退出后回来。

### 4.4 用语

同一组词放在 `src/lib/terms.ts`，按账号类型取：

| | 家庭 | 诊所 |
|---|---|---|
| 方子 | 药方 | 处方 |
| 存药的地方 | 药柜 | 库存 |
| 买药 | 采购 | 进货 |
| 份数单位 | 副 | 剂 |

库存页诊所版：副标题「诊所里每味药还有多少克」，盘点「诊所原本就有的」。处方详情、煎药 / 配药、成本、开方页里的「每副」在诊所里都是「每剂」。

- SQL（`supabase/tests/account_kind_test.sql`）：只能选一次；家庭不能开诊所；`my_workspaces` / `set_active_workspace` / 邀请只认同类型；旧账号（`null`）的函数行为不变；选择后旧的另一种被隐藏但数据还在；`current_context()` 没选类型时不建药柜。
- 单元测试：`terms.test.ts`。
- E2E：
  - 注册时选家庭 / 诊所，各自的导航正确；诊所看不到「比价」、打不开 `/prices`；家庭打不开 `/clinic/*`

- SQL 补充：同类型也不能切换；接受邀请后自己有数据的药柜隐藏；退出后回来，数据都在。
- **升级测试**（`scripts/test-upgrade.sh`，`test-all.sh` 和 CI 都跑）：用 main 的 migration 建库，灌一份像线上的数据（家庭、家人同时在两个家、医生先有空「我们家」再开诊所、两种都有数据的账号、只登录过一次的账号），执行这个 migration 后：

  - 旧代码照常（所有账号 `account_kind = null`）
  - 每种旧账号第一次选类型后：用的是原来的药柜，病人 / 处方 / 库存都在，其他药柜隐藏不删
- 冒烟测试：`login()` 遇到选择页就按账号选好类型；`useWorkspace()` 去掉（一个账号只有一种类型），改成断言类型对。
