# 0007 · CI/CD 与线上检查

- 状态：已实现；部署这一步要在 GitHub 里配好密钥（§5）才会跑
- 日期：2026-10-28
- 作者：Hao、Claude

## 1. 目标

1. 每个 PR 自动跑**和本地一样**的全部测试（`scripts/test-all.sh`），不过不能合并。
2. 合并到 `main` 自动上线：先推数据库 migration，再部署 Vercel，最后对线上跑冒烟测试（smoke test）。
3. 线上每天自动检查一次，坏了能第一时间知道（GitHub 会发邮件）。
4. 密钥只放在 GitHub Actions secrets 和 Vercel，不进仓库。

## 2. 流水线

```
PR / push ──► test ─────────────────────────────── (PR 到此为止)
                │ main
                ▼
              deploy: supabase db push → vercel deploy --prod
                │
                ▼
              smoke: 线上冒烟测试（也每天 13:17 UTC 跑一次）
```

| Job | 做什么 | 文件 |
|---|---|---|
| test | migration 检查 → 类型检查 → lint → 单元测试 → SQL 测试 → E2E（本地 Supabase-lite + 假 OpenRouter） | `.github/workflows/ci-cd.yml` |
| deploy | `supabase db push`（先 `--dry-run` 打日志）→ `vercel deploy --prod`，同一时间只跑一个 | 同上 |
| smoke | Playwright 测线上网址，不启动本地服务 | `.github/workflows/smoke.yml`、`web/e2e/smoke/` |

为什么不用 Vercel 的 Git 集成自动部署：它不知道数据库 migration，可能出现「新代码先上线、表还没改」；也不会等测试通过。所以部署由 GitHub Actions 统一控制。**Vercel 项目不要连 Git 仓库**，否则每次 push 会部署两次（如果以后想要 PR 预览，见 §6）。

CI 不需要 Docker：`scripts/local-stack.sh` 用 runner 自带的 PostgreSQL，PostgREST 和 Supabase Auth 用官方二进制（缓存在 `.local/bin`）。runner 不是 root 用户，满足 Postgres 的要求。

## 3. 数据库 migration 规则

- **只新增，不修改**：`scripts/check-migrations.sh` 在 CI 里和 `main` 比较，已有的 migration 被修改、删除、改名，或者新文件的时间戳排在已有文件前面，都会失败。
- **先迁移、后部署**，所以 migration 必须兼容正在线上跑的旧代码（expand → contract）：
  - 加列、加表、加函数：可以直接做。
  - 删列、改名、改函数签名：分两次上线。第一次让新代码不再使用旧的东西，第二次再删。
- 失败处理：`db push` 每个 migration 在自己的事务里执行，失败的那一个会回滚，部署也就停在这一步，线上代码不变。修复的方法是**再加一个新的 migration**，不要去改失败的那个文件。
- `seed.sql` 不在流水线里跑（它只在第一次建库时需要）。以后要补药材目录，写成 migration。

## 4. 冒烟测试（smoke test）

`npm run smoke`（在 `web/` 里），默认测 `https://mychinesemedicine.vercel.app`，可以用 `SMOKE_BASE_URL` 改。

| 文件 | 需要登录 | 内容 |
|---|---|---|
| `public.spec.ts` | 否 | 登录页、学堂能打开；内部页跳登录；`/api/parse-prescription` 未登录 401；安全响应头 |
| `account.spec.ts` | 是（`SMOKE_EMAIL` / `SMOKE_PASSWORD`） | 登录 → 总览页（自动建好药柜）→ 录一张药方（别名「北芪」→ 黄芪）→ 详情页 → 删除。`SMOKE_PARSE=1` 时再测一次真实拍照识别 |

- 冒烟测试账号是**专门的测试账号**，只在自己的药柜里写数据，写完就删。不要用家人或病人的真实账号。
- 真实识别默认不跑（每次都会花一点 OpenRouter 额度，照片会留在测试账号的存储里），只在手动触发 Smoke 时勾选 `parse`。
- 没配测试账号时，`account.spec.ts` 自动跳过，公开检查照常跑。

## 5. 需要配置的密钥

GitHub 仓库 → Settings → Secrets and variables → Actions → **Secrets**：

| Secret | 从哪里拿 | 用途 |
|---|---|---|
| `SUPABASE_ACCESS_TOKEN` | supabase.com → Account → Access Tokens（新建一个只给 CI 用的） | `supabase link` / `db push` |
| `SUPABASE_DB_PASSWORD` | Supabase 项目 → Project Settings → Database（建项目时设的密码，可以重置） | `db push` 连数据库 |
| `VERCEL_TOKEN` | vercel.com → Account Settings → Tokens（Scope 选 haoliangpao's projects） | `vercel deploy` |
| `SMOKE_EMAIL` / `SMOKE_PASSWORD` | 冒烟测试账号 | `account.spec.ts` |

Project ref、Vercel 的 org / project id 不是密钥，直接写在 `ci-cd.yml` 的 `env` 里。

> Vercel 里的 `TEST_PATIENT_EMAIL` / `TEST_PATIENT_PASSWORD` 应该挪到上面的 `SMOKE_EMAIL` / `SMOKE_PASSWORD`，然后从 Vercel 删掉：网站运行时用不到它们，放在 Vercel 只会多一个泄露的地方。

可选：在 Settings → Environments → `production` 里加 Required reviewers，这样每次上线前要在 GitHub 上点一下批准。

## 7. 上线后发现并修复的问题（2026-10-28）

- Supabase advisors 报的警告：13 个 SECURITY DEFINER 业务函数对未登录用户（anon）开放了 EXECUTE（函数内部都检查 `auth.uid()`，没有实际泄露，但不该开放）；3 个触发器函数可以被直接调用；`match_herb` 没固定 `search_path`；`user_settings` 的 policy 每行都重新算 `auth.uid()`。→ `20261028000009_lock_down_rpc.sql`，SQL 测试 `rpc_privileges_test.sql`（本地 stub 也补上了 `anon` 角色，和 Supabase 一致）。
- 缺少安全响应头（可以被 iframe 嵌入，有点击劫持风险），并暴露 `x-powered-by`。→ `next.config.ts` 的 `headers()`，E2E 和冒烟测试都检查。
- 仍是警告、需要在 Supabase 里手动处理的：Auth 的 Leaked password protection（拒绝已泄露的密码）只有 Pro 计划能开。
- 线上 RLS 用只读事务验证过：模拟一个陌生用户和未登录用户，所有业务表都是 0 行；用户本人能看到自己的 2 个药柜。
