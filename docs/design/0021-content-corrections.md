# 0021 · 信息纠错：指出药材和题目里的错误

- 状态：已实现（第一版）
- 日期：2026-11-15
- 作者：Hao、Claude
- 功能编号：PLAT-5
- 相关：0014（Bug 反馈）、0015（管理员看板）、0010 / 0017 / 0018（药材资料、目录、来源和部位）、0020（学堂题库）

## 1. 为什么

Hao 2026-11-15：「在现在bug report里面，是不是可以允许用户或者医生提出问题说这个药物的归类有问题，出现了信息类的错误，因为大部分仍然是AI做的，所以准确性有待考量。」

现在 App 里大部分「知识」是 AI 整理的，都还没经过医生审核：

| 内容 | 来源 | 审核情况 |
|---|---|---|
| 药材目录 507 味（名字、拼音、功效分类、别名、炮制品对应） | AI 按药典 / 教材整理（0017） | 没有逐条核对 |
| 来源 / 入药部位分类 | AI 整理（0018），约 30 味拿不准 | 没有 |
| 药材资料（性味、归经、功效、炮制、毒性……） | AI 起草（0010） | 等李医生在核对页审核 |
| 默认照片 | Hao 认过 8 张 | 认过，但没请医生看 |
| 学堂题库 123 题 | AI 整理（0020） | 没有，页面上写「发现错误请点右下角反馈」 |

原来只能用右下角的「反馈问题」，但那是给程序问题设计的：不知道说的是哪味药、哪道题、哪一项；还会带上操作记录，对纠错没用。

## 2. 做什么

- 药材详情页：药名下面的标签行旁边有一个小按钮「信息有误？」
- 学堂（每日一题、练一练、复习）：答完以后有「这题有误？」
- 点开是**同一个反馈面板**，但已经选好「信息纠错」、带上了这味药 / 这道题，用户：
  1. 选「哪一项有误」（必选）
  2. 写「应该是什么？」（必填，就是原来的描述，最多 2000 字）
  3. 写「依据」（可选，最多 200 字，比如书名）
- 管理员看板的 Bugs 列表按类型筛选（程序问题 / 信息纠错），信息纠错显示是哪味药 / 哪道题、哪一项、建议和依据；按对象汇总「被指出 N 次」
- **不做**：在看板上一键改数据（§6）

## 3. 数据：复用 `bug_reports`，加几列

**为什么不新建一张表**：纠错和 Bug 反馈的权限（只能插自己的、只能读自己的、不能改不能删）、每天的次数、状态流转、管理员看板、Slack 通知完全一样。复用一张表，这些都不用再写一遍、再测一遍；看板上也是一个地方处理。代价是表上多了几列只有纠错才用的（对程序问题都是空的），用 check 约束管住。

**为什么不改 0014、单开 0021**：0014 记的是已经上线的第一阶段（脱敏规则、按钮白名单），本身已经很长；纠错有自己的一套决定（隐私、字段列表、处理流程）和「待斟酌」。0014、0015 开头加了一句指向这里。

### 3.1 新列（migration `20261115000028_content_corrections.sql`）

```sql
kind                text not null default 'bug'   -- bug（程序问题）/ content（信息纠错）
subject_type        text                          -- herb / quiz_question；程序问题为空
subject_herb_id     uuid → herbs on delete set null
subject_question_id text → quiz_questions on delete set null
field               text                          -- 哪一项有误（§3.2）
evidence            text                          -- 依据，可选，1–200 字
```

- **两个外键而不是一个 `subject_id text`**：外键让数据库保证「只能给存在的药 / 题纠错」（插入时），也方便看板 join 出药名、题干。只有两种对象，两列不算多；以后多一种对象再加一列
- `subject_type` 单独存，不从哪个外键有值推出来：药材被删（合并重复的药）时外键变空，这条纠错还在，`subject_type` 和 `field` 照样说得清「当时说的是一味药的哪一项」，看板显示「（药材已删除）」
- 「插入时必须指向存在的对象」写在一条**限制性 RLS 策略**（`br_insert_subject`，`as restrictive`）里，不写在 check 约束里：check 约束对以后的每一次更新都生效，药材删掉、外键被置空时会违反约束，导致药材删不掉。限制性策略只在用户插入时生效，并且**不用改原来的 `br_insert` 策略**
- 外键用 `on delete set null`：药材 / 题删了，纠错留着（和账号删了反馈留着一样）。题目按 0020 不删、只下架（`retired`），一般用不到

### 3.2 「哪一项有误」

代码在 `web/src/lib/content-correction.ts`（纯函数 + 单元测试），数据库的 check 约束里是同一份列表（单元测试比对 migration 里的列表和代码里的一致）。

| 对象 | `field` | 页面上 |
|---|---|---|
| 药材 | `name` | 药名 |
| | `pinyin` | 拼音 |
| | `aliases` | 别名 |
| | `category` | 功效分类 |
| | `origin_kind` | 来源（植物 / 动物 / 矿物……） |
| | `medicinal_part` | 入药部位 |
| | `base_herb` | 原药材 / 炮制品的对应 |
| | `properties` | 性味归经（只在有资料时可选） |
| | `monograph` | 其他资料：功效、炮制、产区、毒性、使用注意等（只在有资料时可选） |
| | `photo` | 照片（只在显示的是默认照片时可选；本罐照片是用户自己拍的） |
| | `other` | 其他 |
| 题目 | `stem` 题干、`options` 选项、`answer` 答案、`explanation` 解析、`source` 出处、`other` 其他 | |

check 约束 `bug_reports_kind_shape`：

- `kind = 'bug'`：`subject_type`、两个外键、`field`、`evidence` 都是空的（老代码插入时就是这样，默认值保证）
- `kind = 'content'`：`subject_type` 和 `field` 对得上（药材的字段只能配药材）；另一种对象的外键是空的；**不带诊断信息**：`recent_actions`、`recent_errors` 是空数组，`user_agent`、`viewport`、`workspace_id` 是空的（§4）

### 3.3 权限

- 新列的 insert 列级授权给 `authenticated`；`anon` 照旧什么权限都没有。**只有登录用户能提交**，沿用 0014，不给匿名开口子
- 读：照旧只能读自己的（`br_read` 不变）；描述、依据只有提交人和管理员能看
- 每天的次数：照旧，纠错和程序问题**共用**每人每天 20 条（触发器不变）
- 老代码：插入时不写新列，`kind` 默认 `bug`，其他是空的，约束通过；`admin_bug_reports` 不动，老看板照常（会把纠错也列出来，没有新列，只是看不出是哪味药）

### 3.4 管理员函数

新函数 `admin_feedback_reports(p_status, p_limit)`：和 `admin_bug_reports` 一样先 `admin_require()`，返回原来的列 + `kind`、`subject_type`、`subject_id`（药材的 uuid 或题目 id）、`subject_label`（药名 / 题干）、`field`、`evidence`。

**为什么不直接改 `admin_bug_reports`**：返回的列变了，Postgres 只能先删再建；新函数是「先扩展」，线上旧代码在部署前后都能用。旧函数下一次动 `bug_reports` 的 migration 里删（「后收缩」），见 §9 #6。

## 4. 隐私

- **纠错不带操作记录、前端错误、浏览器信息、药柜**：纠错说的是公开知识，定位用不到「点了哪些按钮」。浏览器端不收集，server action 不发，数据库 check 约束再挡一道（直接调 API 塞操作记录也存不进去）
- 带：哪个对象、哪一项、建议、依据、当前页面路径（脱敏规则同 0014）、App 版本（服务器填，知道当时显示的是哪一版的数据）
- 描述（建议）和依据：用户写的，原样存；只有提交人和管理员能读。面板上照旧提示「不要写病人的姓名、电话」
- **Slack**：照旧只发编号、页面、时间，多一行「类型：信息纠错」。不发药名 / 题目（不是隐私，但也没必要：Slack 只是提醒去看板看）、不发建议

## 5. 页面

### 5.1 入口

- **药材详情页**（登录才能看）：药名下面的标签行右边，「信息有误？」。手机上点的区域 ≥ 44px 高
- **学堂**：答完一道题，解析和出处下面「这题有误？」。每日一题、练一练、复习都是同一个题卡组件。
  - 没登录：同一个位置显示「[登录]后可以指出错误」，没有按钮（右下角的反馈按钮也只在登录后有）
  - 「题目由 AI 整理，尚未经医生审核」那句提示改成「发现错误请答完后点「这题有误？」」（没登录：「登录后可以指出错误」）
- 右下角的「反馈问题」不变，仍然是程序问题。不在它里面加「信息纠错」选项：纠错需要知道说的是哪味药、哪道题，从具体的页面进来最准

### 5.2 面板

入口按钮发一个浏览器事件（`content-correction:open`，带对象类型、id、显示的名字、可选的字段），根布局里的反馈组件收到后打开同一个面板，换成纠错的样子：

- 标题「指出信息错误」，下面写「关于：麻黄」或「关于：这道题「……」」
- 「哪一项有误？」下拉，先是「请选择」；「应该是什么？」文本框；「依据（可选）」一行
- 「会附带：这味药 / 这道题、你选的那一项、当前页面的路径。不带操作记录和浏览器信息。」
- 没选哪一项、或者「应该是什么」是空的，提交按钮点不了；服务器也会拒绝
- 成功、失败和程序问题一样（显示编号；失败时写的内容还在，可以再点提交）。纠错的草稿不存 `sessionStorage`（只在页面内存里）：内容短，而且要和对象绑在一起，换了对象就清空
- 程序问题的草稿和纠错的内容分开存，互不覆盖

### 5.3 管理员看板 `/admin/bugs`

- 第一行按类型：全部 / 程序问题 / 信息纠错（带数量）；第二行按状态（数量随类型变）。都写进地址栏（`?kind=content&status=new`），互相保留
- 纠错的状态显示成「新 / 处理中 / 已改 / 不改」（数据库里的值和程序问题一样）
- 每条纠错：「信息纠错」标签、对象（药材链接到 `/herbs/<id>`；题目显示 id 和题干）、哪一项、建议、依据、「这味药 / 这道题被指出 N 次（未处理 M）」
- 选「信息纠错」时，上面多一块**按对象汇总**：每个被指出过的药 / 题一行，按未处理的次数、总次数排，点一下只看这个对象的纠错（`?kind=content&subject=herb:<id>`）
- 数据：一次拿最近 500 条（`admin_feedback_reports(null, 500)`），筛选、计数、汇总在页面里用纯函数算（`content-correction.ts`，有单元测试），最多显示 100 条。500 条以前的不在计数里，现在的量远远不到

## 6. 处理流程（这一版不做「一键改数据」）

看板只改状态。真正改数据还是走原来的路，因为这些数据都以仓库里的 JSON / seed 为准，直接改数据库会和仓库对不上：

| 哪一项 | 改哪里 | 怎么上线 |
|---|---|---|
| 药名、拼音、功效分类、别名、炮制品对应 | `supabase/seed.sql`（目录的正式来源，0017 §4） | 写一个新 migration 明确 `update` 那几味（生成脚本只「补没有的」，不覆盖已有的） |
| 来源、入药部位 | `supabase/data/herb-kinds.json` | 0018 §3.2：生成新 migration，把「只填空的」换成按名字明确 update |
| 性味归经和其他资料 | 草稿：`herb-monographs.json` 或直接在核对页 `/review/herbs/<id>` 改（审核人）；已审核的：核对页 | 核对页改了立刻生效，有修改记录 |
| 照片 | `herb-photos.json`（`scripts/fetch-herb-photos.mjs`） | 生成新 migration；不合适就设 `photo: null` |
| 题目 | `supabase/data/quiz-questions.json`：改内容，或 `status: retired` 下架 | `scripts/gen-quiz-questions.mjs` 生成新 migration（0020 §3.2，按 id 覆盖） |

建议的节奏：

1. 看板选「信息纠错」，先看汇总里被多人指出的
2. 拿不准的（大部分是医学内容）转给李医生看，状态改「处理中」
3. 改了 → 合并上线以后改「已改」；不改（用户说错了、或者是流派差异）→「不改」
4. 攒几条一起改，一个 PR 一个 migration，不用每条一个

## 9. 待 Hao 斟酌的决定

| # | 决定 | 理由 | 备选 |
|---|---|---|---|
| 1 | 复用 `bug_reports` 加 `kind` 列，不新建表 | 权限、次数、状态、看板、通知都一样，复用少写少测；一个地方处理 | 单独一张 `content_corrections` 表（列更干净，但权限、配额、看板要再做一遍） |
| 2 | 纠错和程序问题**共用**每人每天 20 条 | 简单；李医生一天指出 20 处以上的可能性很小，真到了说明该一起坐下来过一遍 | 纠错单独计数，或者给审核人（李医生）放宽 |
| 3 | 纠错**不带**操作记录、前端错误、浏览器、药柜，数据库约束挡住 | 公开知识，用不到；少收一样就少一样风险 | 带浏览器信息（照片显示不对时也许有用） |
| 4 | 只有登录用户能纠错；学堂没登录提示登录 | 沿用 0014，不给匿名开口子（防刷、防骚扰） | 学堂对匿名开放纠错（要加验证码、单独的次数限制） |
| 5 | 看板只改状态，**不做一键改数据**；改数据走 JSON / seed + migration 或核对页（§6） | 这些数据以仓库为准，直接改库会和仓库对不上；一键改还要做审核、撤销 | 以后给药材资料的核对页加「从纠错跳过来」的链接；或者纠错直接生成一个改 JSON 的 PR 草稿 |
| 6 | 新函数 `admin_feedback_reports`，旧的 `admin_bug_reports` 先留着 | 先扩展后收缩：部署前后的旧代码都能用 | 下一次动 `bug_reports` 的 migration 里删掉旧函数（写进 roadmap） |
| 7 | 两个外键（药材、题目）+ `subject_type`，不用一个通用的 `subject_id` | 数据库保证对象存在、看板能 join；只有两种对象 | 通用的 `subject_id text`（加对象类型不用加列，但数据库管不住存在性） |
| 8 | 对象删了纠错留着（外键置空），「插入时对象必须存在」放在限制性 RLS 策略里 | 纠错记录不应该挡住合并重复药材；check 约束做不到「只在插入时」 | 不许删被纠错过的药（外键 restrict） |
| 9 | 药材页的「信息有误？」对所有药都有，包括用户自己加的药 | 用户加的药名字、拼音也可能错（比如拼音是现算的）；药材表本来就全站共用 | 只给目录里的药（有分类的） |
