## 1. 背景与目标

李医生每次开的药方都是纸质的，我们想把它们都存下来，并且管理家里自己买的药材（麦冬、党参、黄芪等，装在玻璃罐里）。

**MVP1 只服务我们自己家**，要回答这几个问题：

1. 我们一共吃过哪些方子？每张方子有哪些药、每味多少克、几副？
2. 某一味药（比如黄芪）出现在哪几张方子里？常用剂量是多少？一共用了多少？
3. 家里每个罐子里还剩多少克？什么时候该补货？
4. 每次在哪家店买的、买了多少、多少钱？（为 MVP2 比价积累数据）

### 不在 MVP1 范围内

| 功能 | 放到 |
|---|---|
| 每副药成本、各家店比价 | MVP2 |
| 医生 / 患者等多角色、医生开方 | MVP3 |
| 药材百科、方剂解读、知识库 RAG | MVP4 |
| 照片识别药材本身 | 往后放（大模型基本已能做） |
| AI 给出用药建议 | **不做**，见 §7 |

## 2. 用户流程

1. **录药方**：手机拍下方子 → AI 识别成「药名 + 克数 + 脚注」→ 人工核对（目录里没有的药名标红）→ 保存。也可以纯手动录入。
2. **记采购**：选店铺（没有就自动新建）→ 填药名、克数、总价 → 保存后自动进药柜。
3. **第一次盘点**：家里原本就有的药材，称重后在「药柜」页录入（记为 `adjust` 流水，不算采购，不影响单价）。
4. **配药**：如果某张方子用家里的药材自己配，在药方详情页点「配 N 副」，自动扣库存。
5. **校准**：随时把罐子称一下，填实际克数，系统写一条差额流水。
6. **家人共享**：Tina 注册后，在总览页输入她的邮箱，两人共用一个药柜。

## 3. 数据模型

完整 SQL 见 `supabase/migrations/20261027000001_init.sql`。

```
workspaces ─┬─ workspace_members ── auth.users
            ├─ prescriptions ── prescription_items ─┐
            ├─ stores ── purchases ── purchase_items ┼── herbs ── herb_aliases
            ├─ inventory_txns ───────────────────────┘     └─ base_herb_id（炮制品 → 原药材）
            └─ pantry_settings（罐号、低库存提醒）
```

### 关键设计决定

1. **`workspaces` 从第一天就有**。MVP1 只有一个「我们家」，但 MVP3 加诊所时，诊所就是 `kind = 'clinic'` 的另一个 workspace，所有表和 RLS 都不用改。
2. **药材目录全局共享**，用户的业务数据按 workspace 隔离。目前任何登录用户都能新增药材，以后加管理员审核。
3. **炮制品单独一行**。炙黄芪和黄芪功效不同、价格不同，不能合并成一行。用 `base_herb_id` 指回原药材，需要时可以合并统计。
4. **别名表**。手写方子常用简称（北芪、枣仁、苡仁、山萸肉），识别出的名字先查标准名、再查别名（`match_herb()`）。
5. **库存用流水账（ledger）**，不存「剩余克数」。库存 = `sum(delta_grams)`。四种流水：`purchase`（采购，由触发器自动写入）、`consume`（配药）、`adjust`（盘点/校准）、`discard`（过期丢弃）。好处：可追溯、不会算乱，以后要看「这个月用了多少黄芪」也直接能查。
6. **克数存的是「每副」用量**，总量 = 每副 × 剂数。方子上写「钱」的，识别时按 1 钱 = 3 g 换算。
7. **价格只存原始数据**（克数 + 总价），单价在视图里算，避免数据不一致。

### 视图

| 视图 | 用途 |
|---|---|
| `v_inventory` | 每味药当前库存、上次采购时间、是否低于提醒线 |
| `v_herb_usage` | 每味药出现在几张方子、剂量范围、累计用量 |
| `v_purchase_prices` | 每次采购的每克单价（MVP2 比价直接用） |

所有视图都是 `security_invoker`，跟随调用者的 RLS。

### 权限（RLS）

- `is_member(workspace_id)` 判断当前用户是否属于该 workspace，所有业务表都按它过滤。
- 子表（`prescription_items`、`purchase_items`）通过父表判断。
- 药方照片存在私有 bucket `prescription-photos`，路径以 `workspace_id/` 开头，按路径第一段做 RLS。

## 4. 照片识别

`POST /api/parse-prescription`

1. 浏览器先把照片缩到长边 1600 px 的 JPEG（手机原图常常 5 MB 以上）。
2. 服务器把照片存进 Supabase Storage。
3. 调用 Claude（默认 `claude-sonnet-5-5`，可用 `ANTHROPIC_MODEL` 改），用 structured outputs 直接拿到 JSON：日期、剂数、患者、煎服法、每味药（名字、克数、先煎/后下等脚注）、不确定之处的备注。
4. 用 `match_herb()` 和目录比对，返回给前端，没匹配上的标红。
5. **一定要人工核对后才保存**。识别结果只是预填表单。

Prompt 明确要求「只转录、不添加、不评价」，看不清的写进 notes，不要猜。

## 5. 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 数据库 / 登录 / 文件 | Supabase（Postgres） | 自带 Auth、RLS、Storage；SQL 是 Hao 的主场；多角色以后几乎不用重写 |
| 前端 + 服务端 | Next.js 16（App Router、Server Actions） | 一个项目同时写页面和后端逻辑；部署到 Vercel 免费 |
| AI | Anthropic SDK（TypeScript），在 Next.js 的 route handler 里调用 | MVP1 只有一个 AI 调用，没必要单独起一个 Python 服务 |
| 数据脚本 | SQL 种子文件；以后批量导入可以加 Python 脚本 | — |

> 和最初讨论的方案相比有一处调整：照片识别先放在 Next.js 里，不单独起 Python/FastAPI 服务。等 MVP4 做知识库（文档切片、向量化）再加 Python 服务。

> 更新（2026-10-27）：后来关闭了 Next.js 16 的 Cache Components，原因见 [0002 §4](0002-decoctions-and-testing.md#4-决定关闭-nextjs-16-的-cache-components)。读数据的组件仍放在 `<Suspense>` 里流式加载。

## 7. 安全边界（贯穿所有 MVP）

- **识别 ≠ 建议**。AI 只做转录和（MVP4 的）科普解读，不对患者给出用药或剂量建议。附子、细辛、半夏等有剂量上限和配伍禁忌，AI 很容易说错。
- **MVP3 之前要处理隐私合规**。诊所使用后系统里就有患者健康信息，在安省受 PHIPA 约束，需要评估数据存放地区（Supabase 可选加拿大区域）、访问日志、患者同意等。
- **版权**。上传的书籍内容可以自己学习使用，公开展示需要授权。

## 8. 待定问题

1. 李医生的方子是手写还是打印？有没有固定格式（抬头、患者信息、剂数写法）？拿一张真实方子测一下识别准确率，再调 prompt。
2. 诊所给的通常是配好的药包，我们自己配药的情况多不多？如果不多，「配 N 副扣库存」这个功能可以弱化。
3. 采购时要不要拍小票识别？（MVP2 可以做，和药方识别是同一套。）
4. Supabase 项目放哪个区域？建议 `ca-central-1`，为 MVP3 的合规打底。
