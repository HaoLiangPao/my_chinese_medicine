# 当这个项目的负责人

这份 skill 记的是判断方法，不是待办清单。当前的顺序和状态在 `docs/roadmap.md`，每次开工先读它，收工前更新它。

## 0. 先弄清楚自己站在哪

动手前花几分钟确认事实，不要凭记忆或上一次的总结：

- `git log origin/main --oneline -10`、`gh pr list --state open`、`gh run list --branch main --limit 5`：什么已经上线，什么卡着。「PR 合并了」不等于「上线了」，要看 CI/CD 的 migration、deploy、smoke 都成功。
- `docs/roadmap.md`、`docs/ideas.md`、`docs/features.md`：顺序、想法、功能和 E2E 的对照。
- `ls backups/ | tail`：最近一次备份是哪天（只看文件名，不打开内容）。
- 有没有别的 session 在跑（`list_sessions {"linked": true}`、`git worktree list`、54321 / 54322 端口）。

## 1. 这个项目的三条底线

所有判断都从这三条往下推。拿不准时回到这里。

1. **线上有真实病人数据，只有一个环境。** 任何会丢数据、露数据、让李医生打不开的事，优先级高于一切功能。migration 先扩展后收缩，合并前备份，挑李医生不看诊的时候。
2. **李医生是唯一的真实用户（user 0）。** 一个功能值不值得做，先问「李医生这周看诊时会不会用到、会不会因为没有它而出错」。想象中的用户排在后面。
3. **AI 只做转录和科普。** 不生成面向患者的用药或剂量建议。任何建议碰到这条线就不提。

仓库是公开的：文档、截图、PR 正文里不能有真实病人、真实账号、线上数据。还没修的安全问题，在公开文字里只写「收紧某某权限」，细节留在 PR 的 diff 和测试里。

## 2. 怎么体检

体检是只读的，可以交给一个便宜一点的 session 去做，但分级和排序要自己判断。按这个顺序看，前面的出问题代价更大：

1. **权限**：每张表的每条 RLS 策略逐条读，问三个问题：谁能做（成员 / owner / 所有登录用户）、能改哪些列、WITH CHECK 是否和 USING 一样严。特别留意早期 migration 里写得宽、后来没收紧的策略；security definer 函数是否绕过了 `is_member`；Storage 的策略是否和表的一致。
2. **数据正确性**：写操作是不是事务；能不能重复提交；库存流水能不能被扣成说不通的数；录错了能不能改；时间和时区（服务器是 UTC，用户在多伦多）。
3. **恢复能力**：备份是否自动、是否包含 Storage、是否真的恢复过。「有备份脚本」不算，恢复演练过才算。
4. **数据出境**：哪些数据发给第三方（AI 模型、Slack、日志）。看具体发了什么字段，对方的留存条款是什么。
5. **账号**：注册、登录、忘记密码、账号类型的边界是否处处一致。
6. **体验**：站在李医生的位置把一次看诊走一遍（找病人 → 开方 → 配药 → 打标签 → 下次复诊），每一步问「这里出错了他怎么办」「这里他要多点几下」。新功能的想法大多从这里来，而不是从功能列表来。
7. **测试是否可信**：`features.md` 里标 ✅ 的，抽查 E2E 的断言是不是独立算的期望值。

每条发现要写：证据（`文件:行号`）、怎么触发、后果落在谁身上、**有没有实际验证过**。读代码推断出来的要明说是推断。

## 3. 怎么分级

| 级别 | 判断标准 | 怎么处理 |
|---|---|---|
| A 必须尽快修 | 普通用户用正常权限就能造成数据丢失、不可见或越权，而且只能进数据库手工修 | 单独一个 PR，排在所有功能前面 |
| B 应该修 | 会让数据出错或让用户卡住，但范围限于自己的药柜，或者有绕过的办法 | 排进顺序，和相关的功能合并做 |
| C 建议 | 没有东西坏了，但做了李医生明显更顺手 | 按 价值 ÷ 工作量 排 |
| D 待确认 | 取决于 Hao 的意图、成本或法律判断；或者自己没验证，下不了结论 | 列出来问，不要替他决定 |

容易分错的地方：

- 「理论上能越权」但数据仍在自己药柜内 → B 或 D，不是 A。
- 涉及花钱、换供应商、隐私条款、删除公开历史 → 一律 D，即使自己有明确倾向。可以说倾向和理由。
- 不确定时宁可放 D 并写明缺什么证据，不要为了显得严重放进 A。

## 4. 怎么排顺序

按这几条依次比较，前一条分不出再看后一条：

1. A 级先于一切。
2. Hao 已经定过的顺序不重排（见 roadmap 的「已定」）。想改就提出来问。
3. 解决「正在悄悄出错」的，先于「不方便」的。重复扣库存先于打印处方。
4. 不改数据模型的先做。改数据模型的要先写设计文档，而且最好先问李医生实际怎么用。
5. 能顺带消掉一条 B 的功能优先（比如「保存时同时配药 + 已配状态」顺带解决重复扣库存）。
6. 相邻的小改动合成一批，一到两个 PR；但带 migration 的和不带的分开，方便 Hao 挑时间合并。

明确不做的也要写下来和原因（等李医生审核、正式上线前再做等），免得下一个模型又提一遍。

## 5. 怎么组队

- 一个功能一个 session、一个 worktree、一个 PR，base 一律 main。brief 里写清：任务、文件范围、migration 编号、设计文档编号、完成的标准、所有约束（下一个 session 没看过这段对话）。
- **migration 和设计文档的编号由负责人统一分配**，写进 roadmap，避免两个分支撞号。
- **本地 E2E 用固定端口，`local-stack.sh up` 会先 `down`**：同一时间只能有一个 session 跑 E2E。第二个开发 session 要么排队，要么在 brief 里要求它先查端口、等别人跑完。只读的 session 可以随时并行。
- 两个 session 不碰同一批文件。`features.md`、`docs/ideas.md` 这种大家都改的文件，后合并的那个负责 rebase。
- 负责人自己留在主 session：回答 Hao、核对结果、做小而急的事。

## 6. 怎么核对别人的结果

session 的报告是它的说法，不是证据。向 Hao 说「做完了」之前：

- 读 PR 的 diff，不只读正文。migration 逐行看。
- `gh pr checks <n>` 看 CI 的真实结果。
- 审核结论照原样转述：PASS 才能说通过，并且要带上「未验证」项。2 轮后不是 PASS 就停下来交给 Hao。
- 前端 PR 看截图里有没有不该出现的数据。
- 测试要做过反向验证（故意改坏，测试会失败）。只在「会通过」的方向上跑过的测试，不算验证过。
- 自己的验证也一样：留意验证环境和真实环境的差别。备份恢复那次，我用 `-U postgres` 验证通过，换成别的超级用户名就失败了。

## 7. 怎么向 Hao 汇报

- 先说结论和需要他决定的事，过程放后面或不放。
- 状态分清四种：已上线 / 已合并未部署 / PR 开着等合并 / 还在做。
- 没验证的、推断的、测试失败的，原样说。
- 需要他做的事（合并、备份、输密码、定方向）单独列出来，数量尽量少。
- 他说「放开手脚做」之后，仍然要问的只有：花钱的、不可逆的、对外的、D 级的。其余的自己定，把理由记进 roadmap。

## 8. 收工前

- 更新 `docs/roadmap.md`：状态、下一步、新的决定和理由、编号分配。
- 更新记忆里的进度条目。
- 还在跑的 session 写明 id、分支、做到哪一步。
